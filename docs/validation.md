# AniBT 重构验证

当前 2.1 使用到期归档策略：仅停止做种并移除 qB 任务，内容文件原地保留。下文 F01–F14 与首次部署数据记录的是 2.0 的历史验证，涉及删除文件的旧策略已撤销。归档验证见文末。

基线是 Python Worker `6ccc7a2`。本轮删除旧 Python 运行时代码、Dockerfile、Compose 和镜像发布流程，交付 Linux amd64/arm64 静态 Worker、systemd 单元及版本部署工具。MediaInfo 为独立系统工具，分析任务在 Worker 内管理。

## 已复现问题的处理

| 原审查项 | 新实现与验证 |
| --- | --- |
| F01 共享目录保护失效 | 目录组件树同时保护所有祖先和后代；排列、标点、重复路径测试与参考实现对照 |
| F02 只回退镜像 | 版本目录绑定可执行文件、配置和单元；激活前恢复数据库，激活后保留最新凭证；部署故障注入测试 |
| F03 媒体坏条目和超时阻塞队列 | 每样本保存进度，失败按条目退避；取消后延后该任务；达到上限可人工处理 |
| F04 媒体和删除竞争 | 持久资源领取与代次校验；删除待确认期间继续保留资源；旧结果不能写回 |
| F05 通知丢失 | 事务发件箱、429 重试、重启恢复、送达后摘要凭证；模拟 Telegram 验证 |
| F06 RSS 修正丢失 | 来源指纹变化撤销尚未提交的准备结果；提交中的哈希先确认；旧领取结果被拒绝 |
| F07 错误订阅污染全局去重 | 拒绝记录限定在订阅内，不生成全局发布成功凭证 |
| F08 历史过期导致重复下载 | 永久内容哈希凭证与临时来源、任务、日志分开；维护后仍去重 |
| F09 取消后数据库延迟写入 | 同步、有上下文的 SQLite 事务和领取校验；真实连接占用下取消排队写入，无延迟提交 |
| F10 停机流量归入当前小时 | 记录连续覆盖区间，长间隔及计数器重置记为未知；窗口按交集统计 |
| F11 热路径扫描全部历史 | 只探测当前哈希，状态变化才更新；任务/凭证计数由事务触发器维护 |
| F12 RSS 重复全量请求 | ETag/Last-Modified 按订阅保存，304 不重复解析、入队 |
| F13 异常 JSON 阻塞批次 | 在入口解析有类型的对象；单条准备失败不会阻塞后续条目 |
| F14 样本上限为 1 却采样 2 个 | 最大文件优先、严格上限；1–20 各上限和多种文件数量测试 |

额外覆盖 qB 增量快照、5.2 结构化添加回执、禁止只读检查发生写操作、真实哈希计算、下载入队与完成分离、共享/缺失文件诊断、显式重试/重放、单实例锁和关机排空。

## 同机合成性能

本机 AMD EPYC 9645，固定 3,000 个现存种子。旧实现采用原审查中的三次中位数；新实现使用 `go test -run '^$' -bench 'Benchmark(Observe|Stats)History' -benchtime=10x` 的每次均值。新实现测量初始化后的稳定观察事务，包含当前暴露数据查询；两者均不包含 qB 网络时间。

| 历史媒体凭证 | 旧观察事务 | 新观察事务 | 旧状态统计 | 新状态统计 |
| ---: | ---: | ---: | ---: | ---: |
| 10,000 | 21.75 ms | 5.01 ms | 1.53 ms | 0.042 ms |
| 100,000 | 123.31 ms | 5.42 ms | 10.78 ms | 0.030 ms |
| 300,000 | 417.86 ms | 6.74 ms | 34.59 ms | 0.034 ms |

新观察事务分配量约 1.55 MiB/次，状态统计约 880 B/次，均未随历史数量增长。Go 的分配量与旧 Python tracemalloc 的峰值定义不同，不用于计算跨语言内存提升比例。这些结果说明历史扫描成本已移出热路径，不代表 qB 上传吞吐有相同比例提升。

## 生产状态迁移演练

对 51 主机的一致性 SQLite 快照验证：10,101 条成功 MediaInfo 凭证全部保留；40 个已入 qB 的下载记录、6 个待媒体上传任务和 21,855 条发布历史迁入新模型，`PRAGMA integrity_check` 返回 `ok`。演练不修改生产任务。正式切换时重新停止旧 Worker 并制作最新快照，数量以当时记录为准。

真实主机只读预检已通过，qB 快照返回 2,995 个种子。对一个 645,146,408 字节的已完成媒体文件，通过受限文件描述符执行 MediaInfo，得到 1 条视频轨、1 条音频轨、2 条字幕轨；未上传、删除或重新校验该种子。Bencode 与共享路径模糊测试分别执行约 7.8 万次和 7.5 万次，未发现失败。

## 原生服务生产验证

2026-10-12 首次迁移后，`anibt.service` 以独立用户运行，`NRestarts=0`，无 TCP/UDP 监听。约 5 分钟观察期内控制循环执行 11 轮，qB HTTP 调用 18 次、失败 0 次，30 个启用订阅均保存 ETag。真实发布 `rel_ToYKyWGNftKH` 完成入队、下载、媒体回传和 Telegram 入队/完成两次通知，成功媒体凭证从 10,101 增至 10,102。

该次资源采样中，服务 cgroup 内存约 42.6 MiB、进程 RSS 约 39.2 MiB，启动期间 cgroup 峰值约 88.2 MiB。迁移前旧 Worker 的 Docker 内存采样约 173.7 MiB。采样时刻和运行阶段不同，此对比只反映观测值，不作为严格的内存性能基准。

旧队列中 6 个 AniBT 媒体接口返回 404 的哈希仍保留为条目重试；这些失败不表示文件丢失，也不阻塞健康任务。未伪造上传成功凭证。凭证错误、限流和上游服务故障会延后依赖通道，不消耗媒体条目的重试次数。

额外回归覆盖采样上限变更后的进度收敛、媒体路径修正后保留旧读取者的资源租约、清理提交次数跨阶段持久化，以及部署停止与激活标记之间的竞争。


## 2.1 归档策略验证

- qB 删除端点唯一调用固定 `deleteFiles=false`；旧 `delete` 命令不可调用。活跃的空闲种子先停止做种，再移除任务。
- 模拟真实文件系统与 qB 接口，证明任务消失后文件内容和目录仍在；重启后只做归档确认，不重复发送移除请求。
- 归档前的媒体任务在确认后继续分析与上传；来源使用新的发布 ID 时，永久哈希凭证仍阻止重复下载。
- 空间不足只暂停新下载；未满 90 天的内容不会因空间不足提前归档或删除。共享目录归档不会删除其他种子的文件。
- qB 任务消失但本地文件缺失时，归档不记成功；达到重试上限后保留清单供人工处理。人工重试回到验证阶段。
- schema 2 到 3 的离线迁移取消未发出的旧删除意图，核对已提交删除的实际结果；不把旧删除记作归档。迁移必须获得 Worker 独占锁。
- 部署测试覆盖升级前快照、迁移失败回退，以及激活后禁止回退破坏性旧版本。

生产状态副本升级演练通过：10,153 条内容身份、10,152 条成功媒体凭证、21,901 条发布身份以及现存媒体任务均原样保留；数据库完整性检查通过。真实 qB 与 AniBT/Telegram 只读预检通过。新配置明确启用每 5 分钟、最多 5 个候选、完成下载后 90 天的归档策略，移除旧清理参数。
